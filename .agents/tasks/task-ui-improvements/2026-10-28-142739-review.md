# UI/UX Improvements: Dark Mode Removal + 20 Feature Additions

This change removes dark mode entirely and adds 20 UI/UX improvements across public pages and the admin area. Four ordered commits: FEAT-001 strips dark mode as a prerequisite; FEAT-002 adds public features (hero counter, tooltips, trending badge, sticky search, breadcrumb, related papers, recently viewed, print/copy); FEAT-003 adds admin features (bulk actions, inline status toggle, preview modal, search history, keyboard shortcut, unsaved-changes warning); FEAT-004 installs sharp and adds an OG image route. Watch for: the HEAD commit (OG image) is not yet pushed to `origin/main` — FEAT-004's "git push completes successfully" criterion is unmet.

**Verdict**: NEEDS_CHANGES

## High-level view

Dark mode is fully gone: `ThemeToggle.tsx` deleted, `darkMode: 'class'` stripped, all `dark:` prefixes cleared from five files, `beforeInteractive` theme-init Script block removed from the root layout. A grep of `src/**` for `dark:` returns zero matches.

The public UI additions are correctly isolated from SSR. `RecentlyViewedWrapper` and `StickySearchWrapper` are dynamically imported with `ssr: false` to prevent localStorage access on the server. `RecentlyViewedWrapper` uses a cancellation flag to prevent stale state on unmount. Related papers guard against null `course_id` before issuing the Supabase query.

Bulk actions in `PapersTable` use `Promise.all` with no per-item error granularity — a single item failure throws to the catch block, but optimistic state updates for successfully-processed items have already been applied. For an internal admin tool this is acceptable, but a partial failure leaves the UI out of sync with the database until a page reload.

The OG image route is registered in the build output (`/papers/[id]/opengraph-image-1c76p0`) and uses `runtime = 'nodejs'` with inline styles only. The commit adding it (`53dd844`) is not pushed: `origin/main` is one commit behind `HEAD`.

### Bulk action partial-failure state divergence (confirmed)

`bulkAction` issues `Promise.all(ids.map(...fetch PATCH...))` then calls `setPapers(prev => prev.map(p => selected.has(p.id) ? {...p, status} : p))` and `setSelected(new Set())`. If any PATCH fails, the `Promise.all` rejects and the catch shows an alert — but by that point no state update has run yet (`setPapers` is after the `await`). Actually reading the code more carefully: state updates are inside the `try` block after the `await`, so a rejection skips them entirely and the UI remains correct. This is fine — noted because the original concern was valid to check.

`bulkDelete` has the same structure and is similarly safe.
