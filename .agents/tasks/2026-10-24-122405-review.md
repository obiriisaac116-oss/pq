# Email integration and contact form (Phase 6)

Phase 6 wires up a contact form end-to-end: a React client component with honeypot and Turnstile CAPTCHA, an API route that chains honeypot → Zod validation → rate limiting → Turnstile verify → Supabase insert → fire-and-forget email, and a Resend helper with HTML escaping. The build and lint both pass clean (Exit code: 0 per phase6-done.md). The implementation is functionally sound and the deliberate ordering decisions (honeypot before schema, lazy Resend client) are correctly motivated. **Watch for:** `aria-describedby` on the name/email/message fields points to per-field error IDs that are never rendered in the DOM (confirmed); the `contactSchema` still validates `honeypot` after the pre-check, creating a latent 400 path for bots (confirmed); and the subject line in the email notification embeds the user-supplied `name` without escaping it (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The API route's ordering correctly places the honeypot pre-check before Zod, but `contactSchema` still carries `honeypot: z.string().max(0)` — a constraint that encodes the same rule out-of-band. If the pre-check guard is ever removed, bots with a filled honeypot get a 400 instead of a silent 200, revealing the field's existence.

The `aria-describedby` wiring on the three visible inputs references IDs (`nameErrorId`, `emailErrorId`, `messageErrorId`) that are never attached to any element in the DOM. The only rendered error element uses `formErrorId`. Screen readers following those references will find nothing, leaving field-level error association broken for assistive technology users.

The Resend email subject is built by string-interpolating `name` directly: `` `New contact message from ${name}` ``. The body is correctly HTML-escaped via `escapeHtml`, but the subject line is a plain string — email clients do not interpret HTML in subjects, but certain mail transport agents and filtering rules process header content, and the raw value is whatever the user submitted (up to 100 chars, any content). This is a low-severity injection surface, but it's inconsistent with the care taken in the body.

Rate limiting fires after Zod validation, which means invalid requests (missing fields, bad email format) bypass the rate limiter entirely. A client could probe field validation rules at arbitrary volume without consuming any rate-limit quota.

### aria-describedby dead references

`ContactForm.tsx` calls `useId()` four times — `nameErrorId`, `emailErrorId`, `messageErrorId`, and `formErrorId`. The form's global error div renders with `id={formErrorId}`. The three inputs pass `aria-describedby={error ? nameErrorId : undefined}`, `aria-describedby={error ? emailErrorId : undefined}`, and `aria-describedby={error ? messageErrorId : undefined}`. None of those three IDs are ever applied to a rendered element. When an error exists, assistive technologies following those `aria-describedby` references will resolve to nothing. The only fix that requires no structural change is pointing all three inputs at `formErrorId` (the element that already exists). A more complete fix would be rendering per-field error messages and attaching the per-field IDs there — but the current API route returns only a single error string, so that would also require a route-side change.

### Email subject injection surface

`escapeHtml` in `email.ts` correctly neutralises `&`, `<`, `>`, `"`, and `'` in the name, email, and message fields used in the HTML body. The subject line is constructed as:

```ts
subject: `New contact message from ${name}`,
```

The `name` value at this point is a validated string (2–100 chars) but otherwise arbitrary. Email headers use `\r\n` as field delimiters; injecting a `\r\n` sequence into a subject can cause header splitting in some MTA configurations. Resend's SDK may already sanitise headers, but the code doesn't guarantee it. Stripping `\r\n` from `name` before embedding it in the subject is a one-line fix that removes the ambiguity entirely.

### Rate limiter placement

The route processes requests in this order: JSON parse → honeypot → Zod → rate limit → Turnstile → DB → email. Because rate limiting comes after Zod validation, any request with a malformed payload exits at step 3 without touching Upstash. Validation error responses (field missing, email invalid, message too short) can be triggered at arbitrary volume from a single IP. Moving the rate-limit check to immediately after the honeypot check closes this gap and adds no meaningful latency to legitimate requests.
